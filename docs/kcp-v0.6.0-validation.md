# kcp-ovo 0.6.0 升级与配对性能复测

日期：2026-11-04。基于 lynn_tcp `04447fb3dcc17f76e535d98a820668420293cded`（v2.4.0）比较 kcp-ovo 0.5.2 与 0.6.0；本次是依赖升级 PR，不提升 lynn_tcp 版本、不发布。历史 [0.5.2 复测](kcp-v0.5.2-validation.md)及其原始数据保持不变。

## 结论

**升级兼容验证通过；有局部吞吐改善，但没有证据证明端到端普遍提速。** 本地默认/全功能及十种独立 feature 组合通过，全功能 225 tests passed，行覆盖 92.97%。新增契约同时在旧/新依赖通过；不改生产传输或 benchmark 参数来换取成绩。

- 128 B、32 并发纯回环：主矩阵吞吐中位数 22289.2 → 26322.0 响应/s（+18.1%）；独立补测 21463.9 → 23561.2（+9.8%）。逐轮并非都改善，TCP 对照也明显波动。
- 同样并发、20 ms RTT / 30% 随机丢包：主矩阵 -11.8%，补测 -4.0%；这是假设性回退信号，不足以定位上游回归，不能被正向结果掩盖。
- 16 KiB、32 并发纯回环：主矩阵 -13.4%，补测 +3.9%，方向不稳定；不可宣称稳定收益或稳定回归。
- 两组共 132 次命令、228 格，均正常退出，无内容校验失败；**不等于每格有业务进展或全部交付**。主矩阵有 1 格 0 请求/0 回复，有限尾部缺失 149；补测缺失 99。完整失败/零值语义、计数与 qdisc 均保留。

原始证据：[配对研究 JSON](benchmark/v2.4.0-arm64-kcp-0.6.0-paired-study.json)，含原 96 次运行、独立 36 次补测、二进制/源码哈希、命令、时间戳、qdisc、验证摘要及实际执行脚本。下表百分比为“新中位数 / 旧中位数 - 1”，不是逐对差异的中位数，也不是统计显著性结论。

## 3. 配对方法与可比性

使用同一 Debian 13-slim 镜像 `sha256:7e3898f7b011a107d0ef7393d5f604a6e0c0ff05ac4f2476630a8af21059ec9b`，新建 OrbStack aarch64 容器，限制 4 CPU、bridge、仅添加 NET_ADMIN，无宿主挂载/host 网络；只改变该容器 lo 的 qdisc。环境及每次实际命令/退出码/时间戳/qdisc/二进制哈希见原始数据。

新旧使用相同源码快照和相同测试，仅 Cargo.toml/Cargo.lock 中的 kcp-ovo 版本及 checksum 不同；锁定依赖通过同一 vendor 源离线构建，`/work/old/target` 与 `/work/new/target` 完全独立。benchmark 和 server 各自记录 SHA-256，明确断言新旧二进制不同；benchmark 的编译期 server 路径仍指向各自目录，未互相覆盖。

- release、`--features kcp`，model 1，128 B，1/32 并发，每连接一个在途请求，每格全新独立 server（4 Tokio workers）；预热 1 秒、测量 5 秒、尾部接收配置 500 ms，单条命令另设 180 秒保护期限。
- 主矩阵三轮：clean、20 ms/0%、1%、5%、10%、20%、30% 丢包，分别 TCP/KCP 和旧/新依赖；按轮与场景交错新旧顺序，偶数轮反转 TCP/KCP 顺序，非随机化研究。
- 非 clean 场景容器 lo 每方向 10 ms delay，loss random X% seed42、limit10000、不限带宽；每个版本/传输命令前重置 qdisc。数据与 ACK 同受包级影响，相同 seed 不代表相同业务轨迹。
- 所有构建、覆盖率与静态检查完成后串行测量，没有本任务的并行构建/其他压测；宿主仍非专用物理机，不能排除外部负载。新旧当前配对比仅与历史旧数比较更有归因价值，但也不是统计显著性证明。
- 请求在本地入队成功后独立计数，以发送开始时间归属测量窗口；响应独立计数并校验内容。分位数仅包含收到的回复，存在缺失截尾偏差；尾部期限可能额外包含发送入队等待，不是严格硬截止。
- qdisc 包含建连、预热及该命令内所有格：原矩阵每命令两个并发格，补测一个；不等于测量期业务丢失率。补测原始元数据沿用 `both cells` 措辞，实际 `clients=[32]` 和单格结果为准，归档保留原文。所有失败/零结果都保留，有限等待内缺失不能认定协议永久丢失。

表中吞吐、p99 分别取三次样本的中位数；不是把 RTT 原始样本合并后的 p99。未测 CPU/内存热点，不把上游减少分配推断为本项目已实测内存收益。

## 8. 复跑与验收

建立专用 Linux 容器（非 host 网络、无宿主挂载，只给 NET_ADMIN），将同一源码复制到 `/work/old`、`/work/new`，只替换旧副本的 Cargo.toml/Cargo.lock 为基线 `04447fb` 对应文件；保留同一新契约测试。两版分别执行 `cargo tree --locked --features kcp -i kcp-ovo` 确认版本，分别 release 编译后再测，不同时构建。可用两 lock 合并 vendor 源离线编译；不得给两版复用 target。

```sh
# Run builds sequentially; do not measure until both finish.
for version in old new; do
  (cd "/work/$version" && cargo bench --locked --offline --features kcp --bench benchmark --no-run)
done
```

JSON 的 `meta.reproduction.main_runner_python` 和 `followup_runner_python` 为实际执行源码，已内置容器检查、独立二进制查找/哈希、轮次顺序、netem 重置、超时及 finally 恢复；分别写到容器 `/work/study.py`、`/work/followup.py` 后串行执行。输出 `/results/study.json` 与 `/results/followup/study.json`，运行前使用全新结果目录，保留异常退出日志；不要在共享或生产容器运行。单次 KCP 命令形如：

```sh
# Only inside the dedicated container; never change the host qdisc.
test -f /.dockerenv
```
