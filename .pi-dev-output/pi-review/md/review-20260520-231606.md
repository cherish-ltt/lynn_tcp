### C3. 领域层违反洋葱架构基本原则（domain → application 反向依赖）

**文件**: `src/domain/handler/handler_system.rs` 第 5 行  
**严重等级**: **Critical**  
**描述**:  
在洋葱架构中，领域层（domain）应该是**最内层**，**不能依赖**应用层（application）或基础设施层（infrastructure）。然而：

```rust
// src/domain/handler/handler_system.rs:5
use crate::application::server::lynn_server::ClientsStruct;
```

`ClientsStruct` 类型（`Arc<DashMap<SocketAddr, LynnUser>>`）是应用层/基础设施层的实现细节。领域层的 `ClientsContext` 可以直接使用 `Arc<DashMap<SocketAddr, LynnUser>>`（从 `std` 和 `dashmap` 引入，这两者是领域层可以接受的依赖），而不需要引用 `application::server::lynn_server::ClientsStruct`。

**影响**:
- 领域层不再"纯"——它依赖于应用层的类型
- 违反了 DDD 的核心原则
- 未来更换 TCP/数据库实现时，领域层代码必须一同修改

**修复建议**:
- 将 `ClientsStruct`/`ClientsStructType`/`TaskBodyOutChannel`/`AsyncFunc` 迁移到 `domain/` 层（或者将 `ClientsStruct` 定义为领域层的类型别名），让 application 依赖 domain，而不是反向

### M2. 公共 API 的 cfg feature guard 差异

**文件**: `src/lib.rs`  
**严重等级**: **Medium**  
**描述**:  
新的 domain/application/infrastructure 模块使用 `pub(crate)` 可见性，而旧的 lib.rs 中 `pub use` 路径依赖的旧模块中部分类型具有不同 feature gate：

| 类型 | 旧路径 | 新路径 | Feature |
|------|--------|--------|---------|
| `ClientsContext` | `super::handler::ClientsContext` | `super::domain::handler::handler_system::ClientsContext` | `#[cfg(feature = "server")]` |
| `HandlerResult` | `super::dto_factory::input_dto::HandlerResult` | `super::domain::model::handler_result::HandlerResult` | `#[cfg(any(feature="server", feature="client"))]` |

新代码中的 feature gate 需要与被替换的旧代码保持一致。我已确认新代码在 `handler_result.rs` 中使用了 `#[cfg(any(feature = "server", feature = "client"))]`，但在 `lynn_user.rs` 中没有 feature gate（它是 `pub(crate)`，仅被 `application/server/lynn_server.rs` 使用，该文件有 `#[cfg(feature = "server")]`），这是正确的。

**不过**，旧 `handler/mod.rs` 中的 `ClientsContext` 有 `#[cfg(feature = "server")]`，新 `handler_system.rs` 中也有 `#[derive(Clone)] #[cfg(feature = "server")]`，这保持一致。✅

### M4. 单元测试失败（预存在）

**文件**: `src/infrastructure/metrics/metrics.rs`  
**严重等级**: **Medium**  
**描述**:  
2 个 histogram 测试失败：

- `test_histogram_observe` - 断言 `metrics_text.contains("lynn_message_size_bytes")` 失败
- `test_timer_helper` - 断言 `metrics_text.contains("lynn_message_processing_duration_seconds")` 失败

**根因**: Histogram 注册到了**自定义 registry**（`registry`）而非默认全局 registry，但 `prometheus::gather()` 只收集默认全局 registry。计数器（Counter）和计量器（Gauge）使用 `register_counter!`/`register_gauge!` 宏默认注册到全局 registry，但直方图使用 `register_histogram_with_registry!(..., registry)` 注册到了自定义 registry，导致 `export_metrics()` 返回的文本中不包含直方图数据。

**注意**: 该问题在**旧代码中同样存在**，属于重构前就已经存在的 bug，并非重构引入的新问题。但重构也未能修复它。
