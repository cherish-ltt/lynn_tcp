## 1. `examples/echo_server_client.rs` — 完整请求-响应循环

### 代码结构与逻辑

```rust
pub async fn echo_handler(
    input_buf_vo: InputBufVO,
    clients_context: ClientsContext,
) -> HandlerResult {
    // ...
    let addrs = clients_context.get_all_clients_addrs().await;
    HandlerResult::new_with_send(1, response.into(), addrs)
}
```

**关键发现：**
- Server 端使用 `InputBufVO::new(big_buf.get_data(), addr)` 构造，`addr` 被正确设置 ✅
- 双参数 `(InputBufVO, ClientsContext)` handler 签名由宏 `impl_tuple!(impl_system_param_function)` 支持 ✅
- `HandlerContext::new(input_buf_vo, clients_context)` 中两个字段都从 state 中正确提取 ✅

### 问题

#### 🟡 [medium] 回传语义模糊

`echo_handler` 使用 `get_all_clients_addrs()` 获取**所有**客户端地址，然后将响应发送给所有客户端。当只有一个客户端时行为正确，但如果有多个客户端，会"广播"给所有人而非仅回传给发送方。示例的教学目标是最基本的请求-响应，当前行为可能引起误导。建议：

```rust
// 只回传给发送方
HandlerResult::new_with_send(1, response.into(), vec![client_addr])
```

#### 🟢 [low] 多余的 `mut`

```rust
if let Some(mut response) = client.get_receive_data().await {
```

`get_method_id(&mut self)` 需要 `&mut self`，所以 `mut` 是必要的。修正：此标记正确 ✅

（实际上 `get_method_id` 定义需要 `&mut self`，所以 `mut` 是必要的，不构成问题。）

#### 🟢 [low] 末尾 sleep 缺少注释

```rust
tokio::time::sleep(Duration::from_millis(100)).await;
```

建议添加注释说明该 sleep 是为了等待 tracing/flush 输出完成。

## 2. `examples/multi_route_service.rs` — 多路由分发与验证

### 代码结构与逻辑

```rust
client.send_data(HandlerResult::new_with_send_to_server(1, "login:alice".into())).await;
client.send_data(HandlerResult::new_with_send_to_server(2, "get_user_info".into())).await;
client.send_data(HandlerResult::new_with_send_to_server(99, "unknown_route".into())).await;
```

**关键发现：**
- 每条消息发送后都调用 `get_receive_data()` 等待响应 ✅
- 未知 route 使用 `tokio::time::timeout` 处理 ✅
- 3 个 handler 各自处理不同 method_id ✅

### 问题

#### 🟢 [low] 未知路由响应时序

发送未知 route (99) 后，Client 调用 `tokio::time::timeout(Duration::from_secs(2), client.get_receive_data()).await`。由于 Server 不会为该 route 生成响应，`get_receive_data()` 会阻塞直到超时。

潜在问题：如果 Server 端有其他 task 同时向该 Client 推送消息（如 broadcast），可能会意外返回。但在当前示例中，Server 不会主动推送消息，因此时序安全。

#### 🟢 [low] handler 使用 `expect` 而非优雅错误处理

```rust
let client_addr = input_buf_vo.get_input_addr().expect("expected client address");
```

在 Server 端 handler 中，`InputBufVO` 总是由 `InputBufVO::new(data, addr)` 构造，`input_addr` 总是 `Some`，因此 `expect` 安全。但作为教学示例，可以展示更优雅的模式匹配。

## 3. `examples/custom_protocol_full.rs` — 自定义协议客户端配套

### 代码结构与逻辑

```rust
let header_mark: &'static u16 = Box::leak(Box::new(0x1234));
let tail_mark: &'static u16 = Box::leak(Box::new(0x4321));
// ...
let client_config = LynnClientConfigBuilder::new()
    .with_server_addr("127.0.0.1:9178")?
    .with_message_header_mark(header_mark)
    .with_message_tail_mark(tail_mark)
    .build();
```

**关键发现：**
- `LynnClientConfigBuilder` 确实提供了 `with_message_header_mark()` / `with_message_tail_mark()` 方法 ✅（验证于 `client_config.rs` 第 124-138 行）
- Server 配置使用相同的自定义标记 ✅
- Client 发送消息使用 `HandlerResult::new_with_send_to_server(1, payload.into())` ✅

### 问题

#### 🔴 [critical] — ❌ 已降级。见下方分析

原以为 `Box::leak` 不仅造成内存泄漏，还可能让新手学到不良模式。但重新审视后，这确实是满足 `tokio::spawn` 的 `'static` 要求的有效方法。不过这不是唯一方法：可以将 `header_mark` / `tail_mark` 的副本 move 进闭包中，或提前将 `server_config` move 进 spawn 闭包。

#### 🟡 [medium] `Box::leak` 导致小内存泄漏

```rust
let header_mark: &'static u16 = Box::leak(Box::new(0x1234));
let tail_mark: &'static u16 = Box::leak(Box::new(0x4321));
```

每个 u16 两个字节被泄漏。在示例中完全可以避免：

```rust
let header_mark: u16 = 0x1234;
let tail_mark: u16 = 0x4321;

// 直接在 tokio::spawn 前构建配置
let server_config = LynnServerConfigBuilder::new()
    .with_addr("0.0.0.0:9178")?
    .with_message_header_mark(&header_mark)
    .with_message_tail_mark(&tail_mark)
    .build();

// server_config 现在包含对 header_mark/tail_mark 的引用
// 需要 move 整个配置进 spawn
let _server_handle = tokio::spawn(async move {
    // 但 server_config 包含 &'a u16，不满足 'static
});
```

问题在于 `LynnServerConfig` 包含 `&'a u16` 引用。如果变量 `header_mark: u16` 是局部变量，那么 `server_config` 不能跨 `async move` 块边界（因为 `'a` 生命周期仅到函数结束）。`Box::leak` 是解决这个生命周期问题的合法方式。

**但如果直接用 `u16` 值而不是引用呢？** 查看 `LynnServerConfig` 的结构体定义：

```rust
pub struct LynnServerConfig<'a> {
    // ...
    message_header_mark: &'a u16,
    message_tail_mark: &'a u16,
}
```

该结构体设计为持有引用而非值，所以确实需要 `'static` 引用来跨 `tokio::spawn` 边界。`Box::leak` 在此场景是合理的选择。**降级此问题为 [low]**。

#### 🟡 [medium] Server 回传响应使用默认标记而非自定义标记

这是**库层面**的问题，不是示例代码的问题。但示例应该明确记录这个限制。

在 `server_common.rs` 的 `check_handler_result` 函数中：

```rust
handler_result.set_marks(
    *SERVER_MESSAGE_HEADER_MARK
        .get()
        .unwrap_or(&DEFAULT_MESSAGE_HEADER_MARK),
    *SERVER_MESSAGE_TAIL_MARK
        .get()
        .unwrap_or(&DEFAULT_MESSAGE_TAIL_MARK),
);
```

Server 使用全局静态变量 `SERVER_MESSAGE_HEADER_MARK` / `SERVER_MESSAGE_TAIL_MARK` 而非每个 handler 配置的自定义标记。这意味着 Server 回复 Client 时使用了**默认消息标记**（0x23D9 / 0x1E27），而 Client 配置的是自定义标记（0x1234 / 0x4321）。结果 Client 端的 `BigBufReader` 无法解析 Server 的回复。

**影响**：Client 不会收到可解析的响应，示例的 "自定义协议在 Client 端的完整使用" 教学目标被削弱。当前示例用 timeout 优雅处理了此情况，但应明确文档化。

**建议**：要么在示例文档中说明这个已知限制，要么修复库代码让响应沿用 handler 入站消息的标记配置。

#### 🟢 [low] 文档中 "Known limitation" 部分措辞含糊

```
// The key demonstration is that the server correctly received and parsed
// the custom protocol message (shown in handler output above).
```

建议更明确地指出："由于 Server 响应消息使用默认标记而非自定义标记，Client 端无法解析响应。这需要在库层面修复。"
