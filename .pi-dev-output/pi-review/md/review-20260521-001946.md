## 中等（Medium）问题

### M1. Builder 模式中的生命周期脆弱性

**文件**: `examples/custom_config_server.rs:37-48`  
**问题描述**: 示例为所有配置值声明局部变量（`max_connections`、`keepalive_time` 等），然后通过 `&variable` 传给 builder。由于 `LynnServerConfig` 的所有字段都是 `&'a` 引用，builder 返回的 config 包含对这些局部变量的借用引用。

虽然当前代码是正确的（配置在 `main` 中创建后立即传递给 `start().await`，而 `start()` 在整个 `main` 生命周期内运行），但这是一个脆弱的模式。如果用户在示例基础上修改代码（例如将 config 移到另一个作用域），将导致悬垂引用。作为教学材料，应该展示更健壮的模式。

**建议**: 
- 使用 `const` / `'static` 常量传递配置值
- 或者在文档注释中明确警告这个生命周期限制

### M2. `broadcast_handler` 在无客户端时静默不输出

**文件**: `examples/basic_server.rs:68-71`, `examples/custom_config_server.rs:111-114`  
**问题描述**: 当 `addrs.is_empty()` 时，handler 直接返回 `HandlerResult::new_without_send()`，无任何输出。作为教程示例，应该明确告知用户当前状态。

**建议**: 添加 `else` 分支输出类似 `println!("[broadcast_handler] No clients connected, skipping broadcast");`

## 低优先级（Low）问题

### L1. `custom_protocol.rs` 文档注释暗示 `get_constructor_id()`/`get_method_id()` 与自定义头尾标记有关

**文件**: `examples/custom_protocol.rs:12-16`（文档注释）  
**问题描述**: 示例的文档注释写道：
> "It also shows how to parse incoming messages using `InputBufVOTrait` methods"
> "- `get_constructor_id()` — Read the constructor ID"
> "- `get_method_id()` — Read the method/route ID"
> "- `get_all_bytes()` — Read the remaining payload bytes"

实际上，`InputBufVOTrait` 的 `get_constructor_id()` 和 `get_method_id()` **不关心消息头/尾标记**——它们只是从消息 payload 的前 3 个字节中读取数据。自定义头尾标记的作用是 TCP 帧的编解码（在 `message_codec.rs` 中处理），与 payload 解析无关。示例代码虽能正常运行，但其**文档注释暗示了两者之间存在关联**，可能误导用户。

### L2. `get_remaining_data_len()` 的输出在 current handler 中始终为 `data.len() - 3`

**文件**: `examples/custom_protocol.rs:67`  
**问题描述**: handler 没有调用任何会修改 `index` 的方法（如 `next_u64()`、`next_u8()`），因此 `get_remaining_data_len()` 始终返回 `data.len() - 3`，与 `all_bytes.len()` 结果等价。展示两个等价的值对读者没有教学价值。建议：要么移除冗余调用，要么添加演示 `next_*` 方法的代码。

### L3. 初始化 `tracing_subscriber` 但 handler 使用 `println!` 而非 `tracing`

**文件**: 所有三个示例  
**问题描述**: 所有示例导入 `tracing_subscriber::fmt` 并调用 `fmt::init()`，但 handler 中全部使用 `println!` 宏，未使用 `tracing::info!` 或 `tracing::warn!`。这本身没有问题（框架可能需要 tracing 初始化），但示例的一致性可以改进。

### L4. `let _server =` 绑定的是 `()` 而非 server 引用

**文件**: 所有三个示例  
**问题描述**: `LynnServer::start()` 返回 `()`，因此 `_server` 的类型实际上是 `()`。传统的 `let _ =` 模式更清晰。当前写法可能让读者误以为 `_server` 持有对 server 的引用。

### L5. `custom_echo_handler` 的 `mut` 声明在阅读时造成困惑

**文件**: `examples/custom_config_server.rs:78`  
**问题描述**: `input_buf_vo` 被声明为 `mut`，因为 `get_method_id()` 需要 `&mut self`。这个约束在 `InputBufVOTrait` 的 API 设计中——`get_constructor_id()` 和 `get_method_id()` 虽然是"getter"，但签名却需要 `&mut self`。这不是示例的问题，但值得指出。
